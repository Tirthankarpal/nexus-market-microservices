Nexus Market — Full-Stack Microservices Architecture & Design Document

Welcome to the definitive system blueprint and design specification for Nexus Market — a high-performance, resilient, and enterprise-grade e-commerce application. This document details the architectural layout, service interactions, security implementations, and frontend-to-backend orchestrations of the entire Nexus Market platform.

🏗️ 1. Global System Architecture

Nexus Market is built using a highly decoupled Spring Cloud Service Mesh on the backend and a reactive React + Vite frontend. Each operational boundary is strictly isolated, utilizing database-per-service patterns, synchronous service-to-service REST communication with dynamic load balancing, and asynchronous event-driven notifications.

🔒 2. Security, Authentication & Gateway Filters

The API Gateway acts as the singular entrance into the system, enforcing edge-level rate-limiting and authorization boundaries before requests ever touch downstream microservices.

🛡️ A. Authentication & Custom Role Propagation

API Gateway uses a global AuthenticationFilter to validate JWT digital signatures. * Public Bypasses: Bypasses authentication for /auth/login, /auth/register, /actuator/**, and GET /api/v1/products (so guests can browse the catalog). * Role Enforcement: If a request attempts a write operation (e.g. POST, PUT, DELETE) on products or inventory, the filter inspects the JWT claims. If the user doesn't possess the ADMIN role, the gateway returns a 403 Forbidden response. * Context Propagation: Once validated, the Gateway strips the Bearer header and injects mutated headers downstream: * X-Authenticated-User: Propagates the subject (username/email). * X-Authenticated-Role: Propagates the role claim (USER or ADMIN). Downstream services rely on these headers rather than validating the JWT again, establishing a zero-trust network interface within the service mesh.

⏳ B. Custom Token Bucket Rate Limiting

To prevent brute-force attacks on identity boundaries, the gateway implements a custom, thread-safe TokenBucket filter running early in the chain (order = -2): * Target Paths: Applied strictly to /auth/login and /auth/register. * Thresholds: Configured with a bucket capacity of 5 tokens and a refill rate of 1 token every 12 seconds (effectively a maximum sustained rate of 5 requests per minute). * Under the Hood: Uses ConcurrentHashMap to track token buckets per IP address. When exhausted, the Gateway returns a detailed JSON body with HTTP status 429 Too Many Requests.

📦 3. Core Microservices Architecture

🛡️ I. API Gateway (api-gateway)

  • Framework: Spring Cloud Gateway (Netty, Reactive Webflux)
  • Port: 8000
  • Key Features:
  • Integrates Resilience4j Circuit Breaker for product routing (productCircuitBreaker).
  • If product-service fails, requests are forwarded to FallbackController at /fallback/product, returning a graceful user-friendly offline message.
  • Dynamically load balances downstream routes using Eureka client-side discovery (lb://).

🔑 II. Authentication Service (auth-service)

  • Port: 8082
  • Database Schema: nexus_auth (table: user_credentials)
  • Endpoints:
  • POST /register: Registers a new user. Accepts UserCredential JSON (username, password, role). Hashes password using BCrypt.
  • POST /login: Validates credentials. Generates a signed JWT with role claim, expiring after default duration, sealed with a strong 256-bit HMAC key.

🏷️ III. Product Service (product-service)

  • Port: 8081
  • Database Schema: product_db (table: products)
  • Key Features:
  • Spring Virtual Threads (spring.threads.virtual.enabled=true): Runs on Java 25. High-throughput concurrency handling designed to minimize thread starvation during heavy blocking database access.
  • Exposes standard CRUD endpoints with built-in Spring Data pagination (Page<Product>).
  • Endpoints:
  • GET /api/v1/products: Paginated, sortable catalog access (public).
  • GET /api/v1/products/{id}: Single product access.
  • POST /api/v1/products: Product creation (Admin only).
  • PUT /api/v1/products/{id}: Product updating (Admin only).
  • DELETE /api/v1/products/{id}: Product deletion (Admin only).

📊 IV. Inventory Service (inventory-service)

  • Port: 8084
  • Database Schema: inventory_db (table: inventory)
  • Key Features:
  • Concurrency Guarantees: Employs @Lock(LockModeType.PESSIMISTIC_WRITE) query overrides when fetching rows for deduction. This locks database rows at the transaction level, preventing concurrent modifications and assuring zero-risk race conditions when multiple orders deduct the same product.
  • Endpoints:
  • GET /api/v1/inventory: Bulk SKU availability queries.
  • PUT /api/v1/inventory/deduct: Deducts quantities from specified SKU.
  • POST /api/v1/inventory: Creates/increments SKU stock (Admin only).
  • PUT /api/v1/inventory/set: Overrides absolute SKU stock quantities (Admin only).

🛒 V. Order Service (order-service)

  • Port: 8083
  • Database Schema: order_db (tables: orders, order_items)
  • Key Features:
  • Synchronously orchestrates inventory checking and deduction before finalizing order creation.
  • Relies on standard transactional boundaries (@Transactional). If stock deduction succeeds but order validation fails, modifications rollback gracefully.
  • Endpoints:
  • POST /api/v1/orders: Places a new order. Reads credentials from X-Authenticated-User header.
  • GET /api/v1/orders: Order history. If X-Authenticated-Role is ADMIN, returns all orders. Otherwise, filters to only retrieve the active user's orders.

📧 VI. Notification Service (notification-service)

  • Port: 8085
  • Database: None (Stateless)
  • Key Features:
  • Asynchronously listens for messages on the Kafka broker.
  • Consumes from topic order-placed under the consumer group notification-group.
  • Logs the mock email receipt dispatch confirming order details.

🗄️ 5. Database Schema & Initialization

Nexus Market deploys PostgreSQL 17-alpine containerized as the global database engine. To enforce schema decoupling, the database engine initializes multiple isolated databases via init-scripts folders mounted inside docker:

Database Seeding Specifications:

  1. init.sql: Automatically executed upon first launch to build isolated service schemas: sql CREATE DATABASE product_db; CREATE DATABASE order_db; CREATE DATABASE inventory_db;
  2. seed_products.sql: Seeds the catalog within the product_db database.
  3. seed_inventory.sql: Seeds identical SKU stock level counterparts inside the inventory_db database, ensuring alignment of initial records (e.g. Nexus Quantum Laptop, Omni Pro Curved Monitor, Holographic Mech Keyboard, etc.).

💻 6. Frontend Architecture (React + Vite)

The frontend is a modern SPA designed using React + Vite, utilizing custom context providers, modern grid layouts, smooth CSS mesh transitions, and beautiful interactive feedback panels.

🧭 A. Routes

  • /catalog: Displays high-performance inventory with responsive grid cards.
  • /login & /register: Custom, premium glassmorphism input screens with full verification state.
  • /cart: Review selections, update quantities, check threshold limit boundaries, and execute checkout.
  • /admin: Admin console showing real-time metrics (Total Catalog Valuation, Out of Stock totals, etc.), catalog updating tables, and product creators.

🌐 B. Global Context Architecture

  1. AuthContext:
  2. Stores user state, login credentials, and session tokens.
  3. Leverages browser-level base64 JWT payload parsing (parseJwt()) to dynamically read authentication details and populate the client-side role (ADMIN or USER) reactively.
  4. CartContext:
  5. Reactively binds cart items according to active authentication.
  6. Guest Mode: Saves and updates anonymous cart details under local storage key cart.
  7. Session Sync: Upon successful registration or login, guest items are automatically adopted and migrated into the user's specific storage bucket (cart_<username>), clearing guest entries immediately.
  8. Reactive Segregation: Once logged out, the active checkout view switches back to guest mode or remains empty.

🎮 C. Robust Fallbacks: Offline Simulator Mode

The frontend is built to be resilient. If the gateway backend is offline or its databases are empty during catalog retrieval, the frontend triggers Offline Simulation Mode: * Action: Catches the network exception and displays a friendly notice panel (Offline Simulation Active). * Simulation Data: Dynamically loads 8 premium offline dummy products, enabling seamless local testing of cart adjustments, pagination configurations, grid filters, and responsive panel rendering without backend dependencies.

🚀 7. Key Production Configuration Parameters (Spring Boot)

For optimal service mesh scaling, downstream Spring Boot microservices utilize these advanced parameters inside application.properties:

  • Spring Threads Virtual: properties spring.threads.virtual.enabled=true Allocates lightweight Java Virtual Threads for request execution, reducing resource footprint and speeding up asynchronous context switching under heavy database locking phases.
  • Hikari Database Connection Pool Limits: properties spring.datasource.hikari.maximum-pool-size=20 spring.datasource.hikari.connection-timeout=30000 spring.datasource.hikari.idle-timeout=600000 spring.datasource.hikari.max-lifetime=1800000 Saves connection allocation delay, preventing requests from hanging indefinitely and releasing idle database connections efficiently.
